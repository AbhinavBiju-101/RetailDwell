Sending data

curl -X POST {{ host }}/api/ingest/v1/tracks \
  -H "Authorization: Bearer YOUR_KEY" \
  -H "Content-Type: application/json" \
  -d '{"layout": "{{ layouts[0].key if layouts else 'A' }}", "recording": "Live",
       "points": [{"track_id": 1, "t": 0.0, "x": 2.1, "y": 3.4}]}'

Each point has exactly four fields and a request holds up to 5,000 points. Anything else is rejected, never stored. Send t in seconds and x, y in metres from the bottom-left corner of the floor.

Sales (POS)

Upload sales for a recording and each sale is tied to the shopper who paid at that moment, which gives revenue per shopper and a buy rate for every zone. The match uses time and place at the register only. A layout needs a zone of type checkout and at least one recording.

Exactly four columns are read: txn_id, t (seconds since the recording started, the same clock as the tracks), zone (the section the items belong to) and amount, one row per section of a basket. Card, loyalty, cashier and customer columns are dropped, and uploading again replaces the earlier file. Till and camera clocks may differ by up to two minutes: the gap is found automatically.

Sending sales from the till

curl -X POST {{ host }}/api/ingest/v1/sales \
  -H "Authorization: Bearer YOUR_KEY" \
  -H "Content-Type: application/json" \
  -d '{"layout": "{{ layouts[0].key if layouts else 'A' }}", "recording": "Live",
       "sales": [{"txn_id": "T1001", "t": 912.4, "zone": "Produce", "amount": 240.0}]}'

Each line has exactly four fields, up to 1,000 lines per request and 5,000 sales per recording. A line with the same txn_id and zone replaces the earlier one, so a retry is safe. Use the same recording name as the camera agent.
